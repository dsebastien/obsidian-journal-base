# 2026-11-16

## Fix #55 — embedded note editors were never destroyed

### How it was found

In a large vault (about 60,000 files, 62 plugins) Obsidian froze for 4 to 5 seconds
every 5 to 10 seconds. A CPU profile of the renderer, taken through
`webContents.debugger`, showed 86% of the time in Dataview's `buildInlineFields`.
That function runs on every editor update and its cost grows with the square of
the document length. TaskNotes dispatches an update to every editor on each task
change. Patching `EditorView.prototype.update` showed that most of the time went
to ONE editor that was not in the DOM: a leaked card editor of the Periodic
Review view, holding a 3.2 MB monthly note. The view was closed at that point.

### Root cause

`Component.unload()` in Obsidian is a no-op on a component that was never loaded:

```js
unload(){if(!this._loaded)return; ...}
```

- `NoteCard` was created with `new NoteCard(...)` and never loaded (no `load()`,
  no parent `addChild(card)`). Every `card.unload()` in both views did nothing.
- `NoteCard.addChild(editor)` therefore never loaded the `EmbeddableEditor`, so
  `removeChild(editor)` never ran `EmbeddableEditor.onunload()`, the only place
  that called `editor.destroy()`. This also leaked one editor per mode change.
- `resolveEditorPrototype()` had the same pattern: the temporary embed is never
  loaded, so `widgetEditorView.unload()` left its editor alive (one per session).
- `MarkdownRenderer.render(..., card)` attached the children of each reading-view
  render to the card, which never unloaded them.

### Fix

- `NoteCard` and `FoldableColumn` call `this.load()` in their constructor. The
  existing `unload()` calls in the views now do what they say.
- `EmbeddableEditor.destroy()`: public, safe to call more than once, independent
  of the load state. `onunload()` calls it, and `NoteCard.destroyEditor()` calls
  it directly after `removeChild()`.
- `destroy()` sets `isDestroyed` first and the `onUpdate` wrapper checks it, so no
  update that arrives during the teardown can reach `onChange` and be saved as
  the note content. It also clears `workspace.activeEditor` when that still
  points at the owner of the destroyed editor.
- `resolveEditorPrototype()` destroys the probe editor directly.
- `NoteCard.loadContent()` checks after the file read that the card is still
  loaded and that no newer load started (a load counter). Before, a card that
  was unloaded during the read created an editor with no owner, and two
  overlapping loads created two editors.
- Each reading-view render gets its own child component, removed before the
  next render.
- `PeriodicReviewView.onunload()` calls `setActiveFileProvider(null)`, like
  `PeriodicNotesView` does. Note: the current Life Tracker plugin has no
  `setActiveFileProvider` method (it has a `fileProviders` array), so both
  calls do nothing today. Open question: move to the new Life Tracker API, or
  remove the provider code.

The rule is in `documentation/Business Rules.md` ("Component Lifecycle").

### Tests

The `Component` mock in `src/test/preload.ts` now follows Obsidian's lifecycle
(copied from the app's code, 1.15.1), with the no-op `unload()` that caused the
bug. `src/test/mocks/editor.ts` adds a fake DOM element, a fake internal editor
and a fake `App` whose `vault.cachedRead` stays pending until the spec resolves

(16 tests). Mutation check: with the two source files reverted, 14 of the 16

`bun run tsc`, `bun run lint`, `bun test` (413 tests) and the production build
are green.

### Validation in Obsidian

Live in notesSeb (Obsidian 1.15.1), counting editors with a census: patch
`EditorView.prototype.update`, make TaskNotes dispatch to every editor
(`emitter.trigger('settings-changed')`), and list the views that got an update
with `dom.isConnected`.

| Step                                                     | 2.1.4                       | With the fix |
| -------------------------------------------------------- | --------------------------- | ------------ |
| Open the Periodic Review view (5 columns)                | 5 live, 1 detached (probe)  | 5 live, 0    |
| Close the tab                                            | 10 detached, none destroyed | 0            |
| Select 4 other periods                                   | not measured                | 5 live, 0    |
| Periodic Notes view: 8 mode changes on a card, 3 at once | not measured                | 1 live, 0    |
| Switch between the two views, then close                 | not measured                | 0            |

No note content changed during these steps, except one: a mode change saves the
editor content even when nothing was edited (see the performance pass), and that
write made Dataview Serializer regenerate a serialized table in the weekly note.

Not verified by hand: typing in a card and closing the view inside the 1 second
save delay. The spec "saves an edit that was made before the card was unloaded"
covers it with fakes only.

### Second leak path: a data update after the view was closed

Found later the same day, during the performance pass: a census showed 17 live
editors in removed view trees (`... < pr-columns < periodic-review-view <
bases-view`), in sets of four. The cause is not the card lifecycle. Bases can
call `onDataUpdated()` on a view that is already unloaded (a queued
notification; it is more likely when the main thread is busy). The view then
ran a full rebuild: new columns, new cards and new editors, in its removed DOM
tree, owned by a view that nothing unloads again.

Reproduced on purpose: open the view, `leaf.detach()`, call
`view.onDataUpdated()`. Before the fix: 5 columns, 4 cards, 4 live editors.
After the fix: 0, 0, 0. The same check showed that such a late update also
arrives on its own after a normal close (5 columns again 300 ms after the close).

Fix: both views keep an `isUnloaded` flag, set first in `onunload()`.
`onDataUpdated()` returns at once when it is set. The Periodic Review view also
checks it in `doDataUpdate()` and cancels its debouncer in `onunload()`.
Spec: `src/app/views/views-unload.spec.ts` (the `BasesView` mock is now a
Component with `app` and `config` from its controller, and the `debounce` mock
has `cancel` and `run`). Mutation check: without the guard, both "after unload"
tests fail.

Note for live tests: a build copied into the vault is reloaded by the Hot Reload
plugin as well (the plugin folder has a `.hotreload` file). A base opened in that
moment shows the view name with no view instance (`controller.view` is
undefined). Wait a few seconds after the copy.

## Performance pass

Measured in notesSeb with the Time base (2,239 entries, Periodic Review with 5
columns), by wrapping the view's methods and forcing data updates with
`controller.notifyView()`.

| Per data update, Periodic Review         | Before | After       |
| ---------------------------------------- | ------ | ----------- |
| `doDataUpdate` total                     | 70 ms  | 10 to 20 ms |
| `PeriodCache.getEntriesByType` (5 calls) | 38 ms  | 1.5 ms      |
| Editor transactions (5 cards)            | 10     | 0           |
| DOM nodes added, 10 updates              | 576    | 98          |

| Periodic Notes view (269 cards) | Before | After |
| ------------------------------- | ------ | ----- |
| DOM nodes added, 10 updates     | 2,850  | 321   |

What changed:

1. **Entries by period type** (`period-cache.ts`, `periodic-note-utils.ts`).
   Each update classified every entry once per column, and `detectPeriodType`
   built and sorted its candidate list for every file. `sortEntriesByDate`
   parsed two file names inside each comparison. Now: `createPeriodTypeDetector`
   builds the candidates once, `groupEntriesByPeriodType` splits the data in one
   pass, and the sort reads each date once, through the date cache of
   `PeriodCache` (which outlives a data version).
2. **Frontmatter fold** (`EmbeddableEditor.foldFrontmatter`). The card re-folds
   on every update (`setDoneState` and `refreshContent`): two transactions per
   card per update, each one a full pass through the editor extensions of every
   plugin. Dataview's inline-field state field costs time in proportion to the
   square of the note length, so this is what made one large note in a column
   freeze the app on every update, with or without the leak. Now the fold is
   dispatched only when `foldedRanges` does not already have that range.
3. **Saves** (`NoteCard.saveContent`). A mode change saved the editor content
   even with no edit, and the delayed save wrote the same content again. Each
   write runs every `modify` listener of the vault (in notesSeb: an index
   rebuild of 0.3 s in Various Complements, Dataview Serializer, Update Time).
   Now the card remembers the content it last read or wrote
   (`lastSyncedContent`) and skips a save of exactly that content. Side effect,
   wanted: a mode change no longer writes stale editor content over a file that
   another tool changed in the meantime.
4. **Card order** (`periodic-notes-view.ts`, `card-order.ts`). Every update
   emptied the card container and added all cards again. Now a signature of the
   rendered list (paths, missing dates, folder, format, template) is kept and
   the rebuild is skipped when it did not change.
5. **Selector rows** (`virtual-period-selector.ts`). `setItems` removed and
   created all rendered rows on every update, and the view then scrolled the
   list back to the selection. Now `haveSameRows` compares the new items with
   the current ones; when the rows are the same, the item data is copied into
   the existing objects (the click handlers read them) and the DOM is kept.
   The view marks and scrolls to the selection only when rows were rendered or
   the selection changed.
6. `NoteCard.setDoneState` touches the DOM only when the state changed.

Checked live after these changes: rows are the same DOM elements across forced
updates, a click on a kept row selects the period and loads its card, the
selection survives updates, the five frontmatter blocks stay folded, and the
census is 0 after close.

### Not done

- `updateVirtualSelector` is now the largest part of an update (about 2 ms per
  column): `filterEntriesByContext` walks all entries of the column type on
  every update. It can be cached on data version and context.
- A card opens any note in an editor, whatever its size. A size limit (show a
  notice and an "open in tab" button above some size) would stop one very large
  note from slowing each update. This changes behaviour, so it needs a decision.
- The Periodic Notes view creates a card for every note of the mode (269 weekly
  notes here). Only expanded cards load content, but the list is not virtual.
- Both views call `setActiveFileProvider`, which the current Life Tracker plugin
  no longer has.
