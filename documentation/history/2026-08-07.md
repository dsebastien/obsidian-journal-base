### THE BLOCKER: `.gitattributes` `export-ignore` broke the reviewer's build

`.gitattributes` carried `CHANGELOG.md export-ignore`. `src/app/whats-new.ts:4` imports
that file as bundled text:

```ts
import changelog from '../../CHANGELOG.md' with { type: 'text' }
```

The reviewer does not clone the repo — it builds the **`git archive`**, and
`export-ignore` strips the file from that archive. So the build failed on their side and
passed on every developer machine and in CI, where the file is present. The symptom
(a module-resolution failure on a file that visibly exists in the repo) points nowhere
near the cause.

`eslint.config.ts` was export-ignored for the same reason and had the same class of
consequence, one step quieter: with no config in the archive the reviewer's eslint falls
back to **its own** ruleset, so what gets reported is not what the repo configured.
`prettier.config.cjs`, `commitlint.config.ts` and `.cz-config.cjs` were dropped from the
list too — cheap to export, and `format:check` reads the first one.

Fixed by shrinking the list to `.github/`, `.husky/`, `.editorconfig`, `.nvmrc`, with the
rule written into `.gitattributes` itself so it is read at the point of edit.

> **RULE — never `export-ignore` a file that the build or the lint reads.** The set that
> must stay exported is everything touched by `bun install`, `bun run build`, `bun test`
> and `bun run lint`, `eslint.config.ts` included. The failure mode is invisible locally
> and only appears in the reviewer's archive build. Also recorded in
> `documentation/Business Rules.md`.

Verify a change to that list by building an actual archive extract, not by reasoning
about it:

```bash
git archive --worktree-attributes --format=tar HEAD | (mkdir -p /tmp/jb-archive && tar -x -C /tmp/jb-archive)
cd /tmp/jb-archive && bun install && bun run build
```

## Debug logging setting wired end to end

### Context

A previous change made `src/utils/log.ts` inert by default: a module-level
`debugLoggingEnabled` flag (default `false`), plus `setDebugLogging()` /
`isDebugLoggingEnabled()`. `log()` early-returns when the flag is off, so no
`console.*` call fires. Needed for the community-catalog review, which flags every
live `console.*` call in shipped code.

Problem: nothing ever called `setDebugLogging()`, so debug logging was unreachable at
runtime. There was no way to turn it on.

### What was done

- `src/app/types/plugin-settings.type.ts` — added `debugModeEnabled: boolean` to
  `PluginSettings`, and `debugModeEnabled: false` to `DEFAULT_SETTINGS`. Must stay
  `false` by default: shipping it on reintroduces exactly the console noise the review
  flagged.
- `src/app/plugin.ts`
    - `loadSettings()` migrates existing `data.json` files with the established pattern:
      `draft.debugModeEnabled = loadedSettings.debugModeEnabled ?? DEFAULT_SETTINGS.debugModeEnabled`.
    - New private `applyDebugLogging()` calls `setDebugLogging(this.settings.debugModeEnabled)`.
      Called at the end of `loadSettings()` on **both** paths (fresh install early-return and
      the migration path), and at the **start** of `saveSettings()` — before its own `log()`
      call, so enabling the setting is visible from that call onwards.
- `src/app/settings/settings-tab.ts` — new `renderTroubleshootingSection()`:
  `Troubleshooting` heading + `Debug logging` toggle. Placed last in `display()`, after
  Periodic Review and before the support/Buy-me-a-coffee block.
- `src/test/preload.ts` — extended the `obsidian` module mock with the base classes and
  helpers that `plugin.ts`'s import graph touches at module-evaluation time
  (`Setting`, `PluginSettingTab`, `ItemView`, `BasesView`, `setIcon`, `debounce`, …).
  Without these, importing `plugin.ts` from a spec throws
  `SyntaxError: Export named 'Setting' not found in module 'obsidian'`.
- `src/app/plugin.spec.ts` (new) — 5 tests: fresh install defaults to `false`; missing
  key in `data.json` defaults to `false`; persisted `true` is restored _and_ applied to
  the logger; persisted `false` leaves logging off; `saveSettings()` applies a flipped
  value immediately in both directions.
- Docs: `README.md` (Getting Started → Troubleshooting), `docs/configuration.md`
  (Troubleshooting Settings table), `documentation/Configuration.md` (setting + wiring).

### Decisions

- **`saveSettings()` is the single choke point** for settings writes — verified by grep,
  not assumed. `settings-tab.ts:255-256` (`updateSettings()`) is the only UI writer of
  `plugin.settings` and always calls `saveSettings()` right after; `syncFromPeriodicNotesPlugin()`
  also routes through it. Hooking `saveSettings()` therefore makes the toggle take effect
  with no plugin reload.
- **`periodic-notes-plugin-settings.schema.ts` left untouched.** It is a zod schema for the
  **external** Periodic Notes plugin's settings — `plugin-integration.service.ts:74` runs
  `safeParse(periodicNotesPlugin.settings)`. It only describes the five period objects and
  must not gain plugin-specific fields, or the sync would reject valid Periodic Notes data.
- Kept the flag-gated `console.*` in `log.ts` rather than reverting to the template's
  commented-out lines. AGENTS.md explicitly sanctions this: "re-enable only behind a
  `debugModeEnabled` settings toggle". The bundle contains the calls but they are
  unreachable unless the user opts in.

### Verification

`bun run format`, `bun run validate` (tsc + 316 tests + lint), `bun run lint:strict`
(`--max-warnings 0`), and `bun run build` all pass.

### Needs manual runtime verification

The toggle itself cannot be self-verified — Obsidian is a GUI app. In a live vault:

1. **Settings → Journal Bases → Troubleshooting → Debug logging** exists, sits after
   Periodic Review and before the Buy-me-a-coffee badge, and is **off** on a fresh install
   and after upgrading from a build without the setting.
2. Turning it **on** makes `Journal Bases: …` lines appear in the developer console
   immediately (starting with `Saving settings`), **without** reloading the plugin.
3. Turning it **off** silences them immediately.
4. The value survives an Obsidian restart (it is persisted in `data.json` and re-applied
   by `loadSettings()`).

### Open questions

None.

## Popout-correct element creation (`obsidianmd/prefer-create-el`)

### Problem

An earlier pass silenced `obsidianmd/prefer-create-el` by replacing
`activeDocument.createElement('div')` with the bare global `createDiv()` at two sites.
The bare global is bound to the **main** document; `activeDocument` resolves to the
**active** window's document, including a popout. That silenced the rule but traded away
popout correctness.

### Fix

Copied the sibling `obsidian-ai-editor` solution (its
`documentation/community-review-checklist.md`, `prefer-create-el` entry).

- **New `src/obsidian-window.d.ts`.** `obsidian.d.ts` declares `createEl`/`createDiv`/
  `createSpan` as bare ambient _functions_ and separately puts `win: Window` on `Node` —
  it never joins the two, so the rule's own suggested spelling (`doc.win.createDiv()`)
  does not typecheck. This file declares the join on `interface Window`. Zero runtime
  code. Verified against **this** repo's obsidian 1.12.0 typings: identical shape to the
  sibling's 1.13.1 (ambient fns at `obsidian.d.ts:192-194`, `Window` augmented at :268
  without them, `Node.win` at :72), so the sibling's file applies verbatim. `tsconfig.json`
  already includes `src/**/*`, so no config change was needed for it.
- Both call sites now use `activeDocument.win.createDiv()`:
  `src/app/services/embeddable-editor.service.ts:112`,
  `src/app/views/periodic-notes/periodic-notes-view.ts:410`.
- **`eslint.config.ts`**: added `DomElementInfo: 'readonly'` to the Obsidian globals.
  `eslint-plugin-obsidianmd` ships this global from 0.4.x; this repo pins **0.1.9**, so
  without it `no-undef` fires on every type-position reference in the new `.d.ts`.

### Verification

- **Detachment preserved.** Both calls are `createDiv()` with **no arguments** — same as
  before, and Obsidian's parentless factory returns a detached element. The receiver is a
  `Window`, which is not a `Node`, so the call can only resolve to the (detached) global
  overload, never to `Node.createDiv` (which appends to its receiver). Neither
  `tempContainer` is appended anywhere: the embeddable-editor one is handed to
  `embedRegistry.embedByExtension.md` and discarded; the periodic-notes one only has its
  `firstElementChild` moved into `cardsContainerEl`.
- **`prefer-create-el` clean.** The rule does **not exist** in the pinned
  `eslint-plugin-obsidianmd` 0.1.9 — it cannot be reproduced by `bun run lint` here; only
  the reviewer's newer plugin reports it. Verified instead by running the 0.4.1 rule
  (resolved from the sibling repo's `node_modules`) with type information against both
  files: **0 problems**. Negative control: a scratch file containing
  `activeDocument.createElement('div')` was reported by the same probe, so the clean
  result is meaningful and not a misconfigured run.
- `bun run format`, `bun run validate` (tsc + 316 tests + lint), `bun run build` all pass.

### Needs manual runtime verification

Popout rendering cannot be self-verified. In a live vault, pop a Journal Bases view out
into its own window (drag the tab out / **Move to new window**) and confirm: the periodic
notes view renders "missing" placeholder cards correctly in the popout, and the embeddable
editor opens and edits normally there.

### Open questions

- Whether to bump `eslint-plugin-obsidianmd` 0.1.9 → 0.4.1 so `prefer-create-el` and the
  other newer rules are caught locally instead of at review time. Out of scope here; the
  bump will surface a batch of new findings.

## `obsidian` typings 1.12.0 → 1.13.1

### Why

1.13.4 is the **latest public** Obsidian release (public since 2026-07-30). Authoritative
source is `latestVersion` in
`https://raw.githubusercontent.com/obsidianmd/obsidian-releases/master/desktop-releases.json`
— `beta.latestVersion` (1.13.5) is Catalyst. `obsidian.md/changelog` still labels 1.13.x
"catalyst" and must not be trusted for this. 1.13.1 is the newest typings on npm; pinned
exactly, never `latest`. The sibling repo `obsidian-ai-editor` made the same bump (see its
`documentation/community-review-checklist.md`, § Typings).

### Changes

- `package.json`: `obsidian` devDependency `1.12.0` → `1.13.1`; `bun install` re-ran.
- `src/app/plugin.ts:38` — `settings` now needs `override`. `Plugin.settings?: unknown`
  is **new in 1.13.0**; `JournalBasesPlugin` narrows it to `PluginSettings`, and
  `noImplicitOverride` demands the keyword (TS4114).
- `src/app/settings/settings-tab.ts:97` — `display()` now needs `override`. In 1.13
  `SettingTab.display()` is a **concrete** member (implementing an abstract member needs no
  keyword; overriding a concrete one does), so TS4114 fired here too.

Those two were the **only** errors the bump surfaced. `minAppVersion` stays **1.10.0** and
`versions.json` is untouched — no newly-used API forces a floor bump; `override` is a
compile-time keyword with zero runtime footprint.

### `display()` is `@deprecated` since 1.13.0 — reported, not papered over

`obsidian.d.ts` marks `SettingTab.display()` `@deprecated Since 1.13.0. Use
getSettingDefinitions instead.` `bun run lint` is **clean** only because
`@typescript-eslint/no-deprecated` is `'off'` in `eslint.config.ts:56` (pre-existing, not
touched here). Probed with the rule flipped to `warn`: it reports **7 call sites** —
`src/app/plugin.ts` 112, 122, 129 and `src/app/settings/settings-tab.ts` 154, 205, 224, 238
(all `this.settingTab.display()` / `this.display()` re-render calls; the declaration itself
is not flagged). No `eslint-disable` was added.

`getSettingDefinitions()` was deliberately **not** adopted. It is all-or-nothing:
`display()` is not called at all when `getSettingDefinitions()` returns a non-empty array,
so adopting it replaces the entire settings UI. This plugin's settings are nested
(`settings.<period>.folder` across 5 period types) with immer-based writes, so it would need
dotted-path `getControlValue`/`setControlValue` overrides — a deliberate port with live-vault
verification, not a lint fix.

`obsidianmd/settings-tab/prefer-setting-definitions` does not exist in the pinned
`eslint-plugin-obsidianmd` 0.1.9 (grepped the package: no matches), so nothing reports it
locally either. The reviewer's newer plugin will.

### Verification

`bun run format`, `bun run validate` (tsc + 316 tests + lint, 0 warnings), `bun run build`
all pass.

### Needs manual runtime verification

None specific to this bump — it is types-only, and `override` emits no JavaScript. The
popout check already noted above still stands.

## `eslint-plugin-obsidianmd` 0.1.9 → 0.4.1, and the findings it surfaced

### Why the bump was the prerequisite

The previous section closed on an open question: "Whether to bump
`eslint-plugin-obsidianmd` 0.1.9 → 0.4.1". It had to be answered first. On 0.1.9
`bun run lint` reported **0 problems**, but that clean result was meaningless — none
of the rules the catalog reviewer actually runs (`prefer-create-el`,
`prefer-window-timers`, `no-global-this`, `settings-tab/prefer-setting-definitions`,
`rule-custom-message`, `eslint-comments/no-restricted-disable`) **exist** in 0.1.9.
Pinned to 0.4.1, matching the sibling `obsidian-ai-editor`.

### The `bun:test` warnings are a Bun-runtime artifact, not a code defect

The bump surfaced 24 problems under `bun run lint`, **17** of them
`obsidianmd/no-nodejs-modules` on the `import … from 'bun:test'` line of every spec
file. They are not real:

- The rule calls `isBuiltin` from `node:module`. Under Bun that returns `true` for
  `bun:test`; under Node it returns `false`. Verified directly:

    ```bash
    bun  -e 'import {isBuiltin} from "node:module"; console.log(isBuiltin("bun:test"))'   # true
    node -e 'const {isBuiltin}=require("node:module"); console.log(isBuiltin("bun:test"))' # false
    ```

- `bun run lint` executes eslint under the Bun runtime, so the whole difference is
  the interpreter. Same eslint, same config, same files:
  **24 problems under Bun, 7 under Node.**
- The rule is auto-`off` when `manifest.isDesktopOnly` is `true`
  (`eslint-plugin-obsidianmd/dist/lib/index.js:190`). The sibling never saw this
  class because it is desktop-only; this plugin is `isDesktopOnly: false`.

No config was changed for these, per the rule below. `bun run lint` therefore reports
17 warnings that `node node_modules/eslint/bin/eslint.js .` does not.

### The rule that governed every decision here

**No `obsidianmd/*` rule may be disabled** — in `eslint.config.ts`, per-file, or
inline. The catalog reviewer runs its **own** ruleset against the source archive, so a
local disable suppresses nothing on their side; it only hides the finding from us
until submission. The sibling learned this when the 0.4.0 review reported all five
rules it had switched off with written rationales. Findings get fixed in code or
reported as-is.

Three pre-existing disables were removed on that basis:

| Was `off`                                         | Now                           | Effect                                            |
| ------------------------------------------------- | ----------------------------- | ------------------------------------------------- |
| `obsidianmd/ui/sentence-case`                     | `error` + declared vocabulary | Was hiding 14 findings                            |
| `obsidianmd/no-static-styles-assignment`          | removed (recommended default) | Already clean — verified by probe                 |
| `obsidianmd/settings-tab/no-manual-html-headings` | removed (recommended default) | Already clean — verified by probe                 |
| `obsidianmd/no-tfile-tfolder-cast: 'warn'`        | removed                       | Redundant restatement of the recommended severity |
| `no-console: 'off'` for `**/utils/log.ts`         | removed                       | `log.ts` no longer needs an exemption (see below) |

### Fixed in code

## Unnecessary type assertions

`@typescript-eslint/no-unnecessary-type-assertion`. Five `as Bases*Option` casts on the
Base view option literals:

- `src/app/views/periodic-notes/periodic-notes-options.ts` — `as BasesDropdownOption`,
  `as BasesSliderOption`, `as BasesToggleOption` ×2;
- `src/app/views/periodic-review/periodic-review-options.ts` — `as BasesToggleOption` ×1.

Each function already returns `BasesAllOptions[]`, and every object literal already
matches its member of that union structurally, so the assertions asserted a type the
value provably had. Deleted, along with the now-unused named imports — both files now
import `BasesAllOptions` only.

The cast was doing real harm, not just noise: an `as` on an object literal suppresses
excess-property checking, so a typo in a `key` or `default` would have compiled. Removing
it puts the literals back under full contextual checking.

Two more casts went in the same batch but under different rules, recorded above:
`(file as unknown as MockTFile)` in the two specs (`no-tfile-tfolder-cast`) and
`globalThis as unknown as { window?: … }` in `src/test/preload.ts` (`no-global-this`).

## CSS `!important` removed (7)

`src/styles.src.css` carried seven `!important` declarations, all in the Periodic Review
responsive breakpoints:

| Block                                   | Declarations                                        |
| --------------------------------------- | --------------------------------------------------- |
| Stacked (narrow) — `.pr-column`         | `min-width: 100%`, `max-width: 100%`                |
| Stacked (narrow) — `.pr-column--folded` | `min-width: 100%`, `max-width: 100%`                |
| Tablet — `.pr-column--folded`           | `min-width: 40px`, `max-width: 40px`, `width: 40px` |

**None was load-bearing**, established by identifying what each rule was actually
fighting rather than by deleting and seeing whether it looked right:

- The only competing declarations are this plugin's **own** earlier rules in the same
  `@layer jb-components` — the base `.pr-column` (0,1,0) and `.pr-column--folded`
  (0,2,0). The breakpoint rules use the same selectors and are declared **later in the
  same layer**, so they win on source order alone.
- Nothing unlayered can be the competitor here: these are plugin-private class names
  (`pr-*`), which no Obsidian core or theme selector targets. That matters because a
  named `@layer` always loses to unlayered CSS regardless of specificity (AGENTS.md,
  "Cascade layers lose to unlayered CSS") — which is exactly why the analysis had to be
  about _who else declares this property_, not about specificity numbers.
- The neighbouring `@apply w-full` in the same rules already relies on the identical
  mechanism to beat `w-[48px]`, and always did so without `!important`.

`src/styles.src.css` now contains a single `!important` occurrence, inside the comment
that records the reasoning above. No `stylelint-disable` was needed.

## Dependency advisories (48) — a stale lockfile, not stale `package.json`

The review reported 48 advisories. Every one was **transitive** and **devDependency-only**
— nothing in the advisory set reaches `main.js`. The root cause was `bun.lock`, not the
manifest: the declared ranges were fine, the resolutions recorded against them were old.

- **`bun update` is a no-op for this.** It re-resolves what `package.json` declares; it
  does not walk the transitive graph a lockfile has already pinned. The advisories sat
  several levels down (`commitizen` → `inquirer` → `external-editor` → `tmp`, the
  `@commitlint/*` tree, the `conventional-changelog-*` tree), so they were invisible to
  it. Refreshing the lockfile itself is what cleared them — the diff moves ~190 resolved
  packages, with no corresponding range change in `package.json`.
- **One entry needed pinning**, because the top of its chain still declares an old range:
  `tmp` 0.0.33 → **0.2.7**, via a new `overrides` block in `package.json`. Reached only
  through `commitizen`; it is a dev tool that never enters the bundle.
- Direct devDependency bumps in the same pass: `commitizen` 4.3.1 → 4.3.2,
  `cz-customizable` 7.5.1 → 7.5.4, `eslint-plugin-obsidianmd` 0.1.9 → 0.4.1,
  `obsidian` 1.12.0 → 1.13.1 (the last two have their own sections above).

> **TRAP — `bun update <pkg>` silently promotes a devDependency into `dependencies`.**
> Naming a package explicitly makes Bun (re-)add it, and it adds to `dependencies`, not
> to the block the package currently lives in. A dev tool moved that way starts shipping.
> Prefer refreshing the lockfile wholesale, or edit `package.json` and re-install. After
> any dependency work, **diff `package.json`'s `dependencies` block** and confirm it is
> still exactly the runtime set — here `@codemirror/language`, `@codemirror/state`,
> `@codemirror/view`, `date-fns`, `immer`, `zod`. It was verified clean.

`bun audit` → **No vulnerabilities found**.

## Deliberate non-fixes

Two review items were examined and deliberately **not** changed. Both are recorded so the
next agent does not "fix" them.

### `settings-tab/prefer-setting-definitions` — all-or-nothing, so it is a port

`display()` is **not called at all** when `getSettingDefinitions()` returns a non-empty
array (`obsidian.d.ts`, `SettingTab.display`). There is no partial adoption: a handful of
declarative rows would **replace the entire settings UI**, not extend it. This plugin's
settings are nested (`settings.<period>.folder` across 5 period types) and written through
immer, so adoption additionally requires dotted-path `getControlValue` / `setControlValue`
overrides. That is a deliberate port with live-vault verification, not a lint fix.

The rule stays enabled and keeps reporting — a local disable would suppress nothing on the
reviewer's side. The sibling `obsidian-ai-editor` reached the same conclusion and tracks
it as its **issue #35**; if this one is ever ported, do both.

### The two capability notes are not defects

- **"Dynamic Code Execution"** is `zod` v4's CSP capability probe — a `new Function("")`
  that zod evaluates to learn whether the host forbids it. It is dependency code in a
  bundled dependency. There is no `eval` and no `new Function` anywhere in `src/`.
- **"Vault Enumeration"** is a **Recommendation**, not a finding, and it is inherent to
  what this plugin _is_: the Base views exist to locate periodic notes across the vault
  and show which periods are missing. Removing the enumeration removes the product.
